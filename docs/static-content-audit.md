# Static / Hardcoded Content Audit — Maram Tours & Travels

Generated by Claude, 5 Sep 2026. Scope: full `src/` tree of `my-shadcn-app`, cross-checked against the Supabase schema (`supabase/migrations/*.sql`) and the admin panel forms. Live queries against the Supabase project (`zuwoodfvntcrnccilytw`) could not be run — this session's network egress blocks `supabase.co` — so "what's in the table" is inferred from schema + admin-form code, not a live row count. If you want an exact row-level check, run the query in the Supabase SQL editor and I can react to the results.

Key insight up front: **the database and admin panel already support almost everything below.** The `packages` table has columns for `itinerary`, `hotels`, `flights`, `departure_dates`, `exclusions`, `optional_tours`, and `cancellation_policy`, and the admin form (`CategoryPackagesTable.tsx`) has tabs to edit all of them. The public package detail page just never reads most of those columns — it renders hardcoded placeholder data instead. So this is overwhelmingly a "wire up the frontend" job, not a "build new backend" job, for the packages section. The Global Visa section is the exception: it has no backend at all.

Severity key: 🔴 High (fake data shown to customers as if real — pricing, flights, hotel names) · 🟠 Medium (generic marketing filler, but not misleading in a way that breaks a booking) · 🟡 Low (cosmetic / dead links).

### 1.2 What this means for priority #1

The single highest-value fix is wiring `PackageDetailClient.tsx` to actually read the columns that already exist and that the admin form already lets staff fill in: `hotels`, `itinerary`, `flights`, `departure_dates`, `exclusions`, `optional_tours`, `cancellation_policy`, `group_size_en/ar`, `accommodation_en/ar`, `meals_en/ar`. Right now, whatever a staff member enters into the admin panel for those fields is saved to Supabase and then **silently ignored** by the customer-facing page. That's worth flagging clearly: staff may already believe they've published real itinerary/hotel/flight data that customers never actually see.

The fabricated pricing/urgency/review content (discount price, "50,620 viewed", fake reviews with fake names) is worth calling out separately since it's not just "static" — it's presenting invented numbers and invented people as if real, on every package, which is a different kind of risk (customer trust, and in some jurisdictions advertising-standards exposure) than a placeholder itinerary is.

### 1.3 Package Listing Pages

- `src/components/packages/PackageFilterBar.tsx` — `continents` filter list is a hardcoded array (not derived from distinct `packages.continent` values in the DB). Low priority, but means a new continent added via admin won't appear as a filter option until code changes.
- `src/components/packages/PackageCard.tsx`, `CommonListingPage.tsx`, `PackageListingLayout.tsx` — these do read from the live `packages` table via the repository/API, so the listing grids themselves are dynamic. Good.
- Category values (`cruise`, `fixed-departure`, `holidays`, `kerala`, `medical`) are hardcoded in both the DB check constraint and the TypeScript types — that's normal/expected, not a bug.

### 1.4 Packages Backend / Supabase

- `supabase/migrations/20260718024643_create_packages.sql` and the bilingual-fields migration define the full schema described above — confirmed by reading the migration files directly.
- `src/lib/packages/types.ts` and `src/lib/packages/mappers.ts` already model every one of those "unused" columns (`PackageRowHotel`, `PackageRowItineraryDay`, `PackageRowOptionalTour`, `PackageRowDepartureDate`, `FlightDetails`) — the typing work to consume them is already done, it's just not called from the detail page.
- I could not run a live `select` against the `packages` table from this session (Supabase's domain is blocked by this environment's egress policy), so I can't tell you exactly how many packages currently have real itinerary/hotel/flight data entered vs. empty. Worth a quick check on your end in the Supabase table editor.

Three different brand domains appear (`maramholidays.com`, `maramtoursandtravels.com`, `travelco.com`), two different phone numbers (a Qatar +974 number and an India +91 number), and the +974 5555 5555 number is repeated as a form *placeholder* in three unrelated forms (`HomeClient.tsx`, `contact/page.tsx`, `BookNowDialog.tsx`) — it reads like a placeholder that was never swapped for a real number. This should be pulled into one config/env value (or a `site_settings` Supabase table) and reused everywhere rather than typed six times.

### 2.5 Global Visa Module (🔴 — no backend at all)

`src/lib/data/visa.ts` (139 lines) is a fully static data file — 14 countries hardcoded with name, flag emoji, description, visa requirements, processing time, and **price** (e.g. "QAR 100" for Qatar). None of this comes from Supabase; there's no `countries`/`visa_types` table in any migration. This is the one area of the site where the gap isn't "frontend not reading the DB" — there's genuinely no database-backed model for visa data yet. If visa pricing/requirements change, someone has to edit this TypeScript file and redeploy.

### 2.6 Medical Tourism Page — `src/app/[locale]/medical-tourism/MedicalTourismClient.tsx` (636 lines)

- Hardcoded hospital partner list, e.g. "Aster Medcity, Kochi, Kerala" (~line 531) — a fixed array of partner hospitals with photos, not read from any table.
- Two fully invented patient testimonials — "Michael Chang" (Singapore) and "Emma Robertson" (Australia) — with fabricated medical-outcome quotes (~lines 580-581). This is the same fake-testimonial pattern as the home page and package detail page.
- Descriptive marketing copy (JCI/NABH accreditation claims, Panchakarma/Ayurveda copy) is hardcoded prose — reasonable for static marketing copy, but flagging since some of it makes specific accreditation claims ("JCI and NABH certified") that should be verified as still accurate before launch.

### 2.7 Kerala Tourism — `src/components/packages/KeralaTourismClient.tsx` (1,219 lines — largest client component in the app)

- Has a hardcoded `themes` array (~line 36) driving a theme filter/toggle; given the file's size there is likely more embedded static content (attractions, itinerary highlights) that would benefit from a closer line-by-line pass if this page is a priority — flagging for a follow-up review rather than full detail here given the size.

### 2.9 About / Contact pages

- `about/page.tsx` and `contact/page.tsx` are static marketing/informational pages by nature (company story, office info) — expected to be hand-written copy, not database-driven, so not flagged as a defect. The one real issue is the contact-info mismatch already covered in 2.1.

### 2.10 Packages/CategoryPackagesTable (admin) — for contrast, what's already dynamic and working

- Bookings, Enquiries, and the packages CRUD admin screens (`BookingsTable.tsx`, `EnquiriesTable.tsx`, `CategoryPackagesTable.tsx`) all read/write through Supabase via the repository layer (`bookings-repository.ts`, `enquiries-repository.ts`, `packages-repository.ts`) and real API routes (`src/app/api/**`). These are correctly dynamic — no action needed.
- Admin auth (`admin-auth.ts`), Supabase server/browser/middleware clients, and the storage/upload helpers (`storage.ts`, `upload-image.ts`) are all live, not stubbed.

## Suggested order of work

1. Wire `PackageDetailClient.tsx` to read `hotels`, `itinerary`, `flights`, `departure_dates`, `exclusions`, `optional_tours`, `cancellation_policy`, and the bilingual `group_size/accommodation/meals` fields instead of the hardcoded builders in `buildSharedData()` and the two layout components — this is the biggest win since the data model and admin UI already exist.
2. Remove or clearly re-scope the fabricated trust signals on package pages and the home/medical pages (fake reviews, fake "viewed this week" counts, fake discount pricing) — either replace with a real reviews table + real pricing fields, or remove them rather than show invented numbers to customers.
3. Consolidate contact info (phone/email) into one source of truth (env var or a `site_settings` table) and fix the inconsistent brand domain/phone number across Header, TopBar, Footer, contact page, and email templates.
4. Fix Footer dead links and mismatched social icons.
5. Decide whether Global Visa should move to a real Supabase-backed table (recommended, since pricing/requirements change over time) or stay as a maintained code file if it's genuinely static reference data.
6. Lower priority: hardcoded home-page hero slides/destinations, Kerala theme data — worth a closer pass if you want the whole home page dynamic, but these read as intentional "featured" marketing sections rather than bugs.
